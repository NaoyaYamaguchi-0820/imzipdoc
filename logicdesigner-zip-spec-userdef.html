IM-LogicDesigner ZIP仕様 - ユーザ定義編

更新日: 2026-08-11

本書は、フロー定義ZIP（logicdesigner-zip-spec-flow.html）と対をなす、ユーザ定義タスク登録ZIP（user_definition.json）を対象とする。テナントに共有登録するユーザ定義タスク（フロー定義編10.4節のkey.type: "userDefinition"が参照する定義本体）自体を登録・移行するための形式である。フロー定義編・ルーティング定義編（logicdesigner-zip-spec-route.html）・関連機能編（logicdesigner-zip-spec-related.html）とあわせて読むことを前提とする。

1. 概要

フロー画面からエクスポートするflow_definition.json形式のZIPとは別に、テナントに共有登録するユーザ定義タスク自体を登録・移行するための、user_definition.json形式のZIPが存在する。フロー側からkey.type: "userDefinition"として参照される定義本体は、フローのZIPには含まれず、この独立したZIPで管理される（フロー定義編10.4節参照）。

本ZIPのuserDefinitions配列の各要素（definitionオブジェクト）は、フロー定義編10.5節で説明したlocalUserDefinition要素のproperties.definitionと同一の形式を持つ。すなわち、フロー内に直接埋め込む（localUserDefinition）か、テナント単位で切り出して共有登録する（本ZIP、userDefinition）かの違いであり、定義データそのものの構造は共通である。

2. ZIP構造

<user-definition-export>.zip
└── user_definition.json

本書が対象とするサンプルはuser_definition.json1ファイルのみで構成されている。公式の「IM-LogicDesigner仕様書」「4.5. インポート・エクスポート」によると、本来のZIP構成にはアイコンデータが付随する。

<user-definition-export>.zip
├── user_definition.json
└── icon_data/
    ├── designer/<iconId>
    └── palette/<iconId>

icon_data/designer/<iconId>・icon_data/palette/<iconId>は、ユーザ定義タスクにアイコンを設定した場合の画像データと見られる（definitionData.iconIdと対応すると考えられるが未確認）。アイコンを設定していないユーザ定義（本書のサンプルはすべてiconId: null）では、このicon_data/ディレクトリ自体が省略される。また、IM-LogicDesignerのエクスポート機能は本来、フロー定義・ユーザ定義・ルーティング定義を含む全データを一括で1つのZIPにまとめて出力するものであり、user_definition.json単体で構成されたZIP（本書のサンプル）は、その一部を切り出した個別エクスポートに相当する（ルーティング定義編2章参照）。

3. トップレベル構造

{
  "userCategories": [ { ... }, ... ],
  "userDefinitions": [ "{...}", "{...}", ... ]
}
キー型説明
userCategories配列ユーザ定義タスクを分類するカテゴリの一覧。フロー定義編のflowCategories（4章）に相当
userDefinitions配列ユーザ定義タスク本体の一覧。フロー定義編のflowDefinitions（5章）と同様、各要素はJSONを文字列化した値（二重エンコード）

4. userCategories

{
  "categoryId": "sample_category",
  "categoryName": "サンプルカテゴリ",
  "sortNumber": 0,
  "iconId": "",
  "localizes": {},
  "displayName": "サンプルカテゴリ"
}

フロー定義編のflowCategories（4章）とほぼ同形式だが、次の相違点がある。

  • iconIdを持つ（flowCategoriesにはない項目）。サンプルでは空文字列
  • parentIdを持たない。ユーザ定義カテゴリがflowCategories同様の親子ツリー構造をサポートするかは未確認

5. userDefinitions と definitionオブジェクト

userDefinitions配列の各要素をJSON解析すると得られるオブジェクトは、フロー定義編10.5節で説明したlocalUserDefinition要素のproperties.definitionと同一の形式（definitionId・version・categoryId・definitionType・definitionName・sortNumber・definitionData）を持つ。

項目説明
definitionId定義ID。フロー側からkey.type: "userDefinition"として参照する場合、key.idにこの値を指定する（フロー定義編10.4節）
version定義のバージョン
categoryIduserCategories内のcategoryIdを参照
definitionType定義の処理種別。確認できているのは"sql"・"javascript"・"rest"（6〜8章）。他の値は9章参照
definitionName定義名（デザイナ上の表示名）
sortNumber表示順
definitionData.elementId実処理を行う内部要素ID。definitionTypeごとに固定値を取る（6〜8章）
definitionData.elementProperties内部要素固有の設定。definitionTypeごとに構造が異なる（6〜8章）
definitionData.inputDataDefinition / outputDataDefinitionこの定義固有の入出力データ定義（構造はフロー定義編9章と同様）
localize多言語情報（単数形）。カテゴリ・フロー・変数等で使われるlocalizes（複数形）とは綴りが異なる点に注意する。サンプルでは空オブジェクトだったため、多言語名を設定した場合の内部構造は未確認

6. definitionType: "sql"

definitionType: "sql"の場合、definitionData.elementIdは"im_queryExecutor"で、SQL実行に関する設定をelementPropertiesに持つ。

"definitionData": {
  "elementId": "im_queryExecutor",
  "iconId": null,
  "elementProperties": {
    "query": "SELECT column1 FROM sample_table",
    "queryType": "SELECT",
    "databaseType": "TENANT",
    "connectId": "default",
    "limitation": false
  },
  "inputDataDefinition": { "entrypoint": {...}, "typeDefinitions": [...] },
  "outputDataDefinition": { "entrypoint": {...}, "typeDefinitions": [...] }
}
項目説明
query実行するSQL文（2Way-SQL）
queryTypeクエリ種別（SELECT・INSERT等）
databaseTypeデータベース種別（例: TENANT＝テナントDB）
connectId接続ID
limitation範囲指定（取得件数制限）の有無

7. definitionType: "javascript"

definitionType: "javascript"の場合、definitionData.elementIdは"im_scriptExecutor"、definitionData.elementPropertiesはscript（JavaScriptのソースコード文字列）を1項目のみ持つ。

"elementProperties": {
  "script": "/**\n * run.\n *\n * @param input {Object} - task input data.\n * @return {Object} task result.\n */\nfunction run(input) {\n\n\tDebug.console(input.param1, input.param2);\n\n\treturn {\n\t\tmessage: 'hello world.' + input.param1 + '/' + input.param2\n\t};\n}\n"
}

スクリプトはfunction run(input) { ... }という関数を定義する形式で記述する。inputにはinputDataDefinitionで定義した入力データが渡され、戻り値のオブジェクトがoutputDataDefinitionで定義した出力データとして扱われる。サンプル中ではDebug.console(...)によるログ出力が使用されている。

スクリプト内では、原則としてim-BizAPI（Java業務コンポーネント群）を利用できる。ただし公式の「IM-LogicDesignerチュートリアルガイド」「参考：ユーザ定義（JavaScript）における制限」によると、次の基準に該当するAPIは利用できない。制限対象のAPIを呼び出すと、該当APIが存在しない旨のエラーで失敗する。

  • テナント管理などクリティカルな処理を行うことが可能なシステム管理系API
  • システムプロセスの呼び出しや外部スクリプトの呼び出しを行うAPI
  • 画面遷移を伴うAPI

制限対象APIの具体的な一覧はドキュメントには明記されておらず、製品内の denylist 設定（WEB-INF/classes/META-INF/logic/jssp/blacklist）で管理されている。

8. definitionType: "rest"

definitionType: "rest"の場合、definitionData.elementIdは"im_httpclient"で、外部REST APIをHTTP呼び出しするための設定をelementPropertiesに持つ。

"elementProperties": {
  "endpointExpression": "https://example.com/api/resource/1",
  "requestMethod": "GET",
  "requestType": "x-www-form-urlencoded",
  "requestHeaderNames": ["User-Agent"],
  "requestHeaderExpressions": ["LOGIC-DESIGNER INTRAMART/8.0 Version/8.0.0"],
  "requestEncoding": "UTF-8",
  "requestFormKeys": [],
  "requestFormValueExpressions": [],
  "followRedirect": true,
  "requestTimeoutInSeconds": 30,
  "responseType": "json",
  "responseEncoding": "UTF-8",
  "checkStatusCode": true
}
項目説明
endpointExpression呼び出し先URL。公式の「IM-LogicDesignerチュートリアルガイド」「参考：より高度なREST APIの呼び出し」によると、リクエストパラメータだけでなくエンドポイントやヘッダにも${...}形式のEL式を埋め込み、$inputの値を用いて動的に指定できる
requestMethodHTTPメソッド（GET等）
requestTypeリクエストボディのエンコード形式（例: x-www-form-urlencoded）
requestHeaderNames / requestHeaderExpressionsリクエストヘッダのキー・値。同じ添字同士が対になる並行配列
requestEncoding / responseEncodingリクエスト／レスポンスの文字コード
requestFormKeys / requestFormValueExpressionsフォームパラメータのキー・値。requestHeaderNamesと同様の並行配列
followRedirectリダイレクトを追跡するか
requestTimeoutInSecondsタイムアウト秒数
responseTypeレスポンスの解釈形式（例: json）
checkStatusCodeHTTPステータスコードを検証するか

outputDataDefinitionは、この要素固有の固定構造を持つ。status（statusCode・reasonPhraseを持つオブジェクト）、headers（map型）、body（レスポンスボディをパースした内容）、failureResponseBody（失敗時のレスポンスボディ）の4項目が固定で存在すると見られる。bodyの型定義について、公式の「IM-LogicDesignerチュートリアルガイド」によると、レスポンス種別をjsonに設定した上で、返却値のbody<object>を選択して「JSON入力」機能でサンプルJSONを入力すると、対応する型定義（typeDefinitions）が自動生成される。

9. definitionType: "template"

definitionType: "template"の場合、definitionData.elementIdは"im_templateProcessor"で、テンプレート文字列から出力を生成するための設定をelementPropertiesに持つ。IM-Copilotのアシスタント（関連機能編参照）で、LLMへ渡すプロンプトを組み立てる用途で使われている例を確認した。

"elementProperties": {
  "localizedTemplate": { "ja": "", "en": "", "zh_CN": "" },
  "defaultTemplate": "<#setting url_escaping_charset=\"UTF-8\">\nこんにちは、${name}さん。\n参考情報:\n${referenceInfoJson}\n"
}
項目説明
defaultTemplateテンプレート文字列。<#...>ディレクティブや${...}による変数展開の構文（Apache FreeMarkerの構文と一致する）が使われている
localizedTemplateロケールごとのテンプレート文字列の上書き（ja・en・zh_CN等）。サンプルではすべて空文字列で、defaultTemplateのみが使われていた

inputDataDefinitionには、テンプレート内で${...}により参照する変数を持つオブジェクト（サンプルではdataという名前の複合型プロパティの中に、実際に参照する値を格納）に加えて、基本型localeを持つlocaleという名前のプロパティが存在した。outputDataDefinitionは、展開結果の文字列を1項目（output、string型）持つ単純な構造。

localeは、フロー定義編9.2節の基本型一覧に未掲載の型である。テンプレート処理時のロケール（localizedTemplateのどのロケール版を使うか等に関わると考えられる）を表す基本型と見られる。

10. その他のdefinitionType（未確認）

公式の「IM-LogicDesignerチュートリアルガイド」「5.4. ユーザ定義の作成」によると、ユーザ定義タスクの処理種別には、本書でdefinitionDataの内部構造まで確認できている"sql"・"javascript"・"rest"・"template"に加えて、次の7種類が存在する。

  • Database Fetch
  • CSV Fetch
  • Excel入力
  • Excel出力
  • XML解析
  • HTML解析
  • BIS申請/承認

これらのdefinitionType文字列そのもの、およびdefinitionDataの内部構造（elementId・elementProperties）は、ZIPの実データでは未確認である。

11. 新規ユーザ定義ZIP生成手順（実践ガイド）

フロー定義編18章と同様、専用の生成ツールを介さず、本書の内容だけを頼りにゼロからuser_definition.jsonとZIPを組み立てる場合の実践的な手順をまとめる。

11.1 全体の手順

  1. userCategoriesを用意する（最低1件）。4章参照。
  2. definitionオブジェクト（二重エンコード前の生JSONオブジェクト）を5章の項目一覧に従って組み立てる。definitionTypeに応じてelementId・elementPropertiesを設定する（6〜9章）。
  3. inputDataDefinition・outputDataDefinitionを組み立てる（構造はフロー定義編9章と同様）。definitionType: "rest"の場合のoutputDataDefinitionは8章の固定構造に従う。
  4. definitionオブジェクトをJSON.stringifyし、userDefinitions配列の要素（文字列）として格納する（二重エンコード、5章）。
  5. トップレベル{ userCategories, userDefinitions }をJSON化し、UTF-8でuser_definition.jsonとして保存する。
  6. 11.3節のセルフチェックリストで整合性を確認する。
  7. ZIPへパッケージングする（user_definition.jsonをルート直下に配置。2章）。
  8. このユーザ定義を参照するフローを生成する場合は、フロー定義編18章の手順に従い、flowElements側でkey.type: "userDefinition"・key.id: "<definitionId>"として参照する（フロー定義編10.4節）。

11.2 最小スケルトン（javascript例）

フロー定義編で実際に組み立て・実行を確認できたdefinitionType: "javascript"の構成を、二重エンコード前の形で示す。

{
  "userCategories": [
    {
      "categoryId": "sample_category",
      "categoryName": "サンプルカテゴリ",
      "sortNumber": 0,
      "iconId": "",
      "localizes": {},
      "displayName": "サンプルカテゴリ"
    }
  ],
  "userDefinitions": [
    {
      "definitionId": "sample_definition",
      "version": 1,
      "categoryId": "sample_category",
      "definitionType": "javascript",
      "definitionName": "サンプル定義",
      "sortNumber": 100,
      "definitionData": {
        "elementId": "im_scriptExecutor",
        "iconId": null,
        "elementProperties": {
          "script": "function run(input) {\n\treturn {\n\t\tmessage: 'hello'\n\t};\n}\n"
        },
        "inputDataDefinition": {
          "entrypoint": { "typeId": "root", "basic": false, "required": false, "listingType": "none" },
          "typeDefinitions": [ { "id": "root", "properties": [] } ]
        },
        "outputDataDefinition": {
          "entrypoint": { "typeId": "root", "basic": false, "required": false, "listingType": "none" },
          "typeDefinitions": [
            { "id": "root", "properties": [
              { "typeId": "string", "name": "message", "description": null, "listingType": "none", "required": false, "basic": true }
            ] },
            { "id": "string", "properties": [] }
          ]
        }
      },
      "localize": {}
    }
  ]
}

この内側のuserDefinitions[0]オブジェクトをJSON.stringifyして文字列化し、userDefinitions配列の要素として格納する（二重エンコード）点に注意する。

11.3 生成後セルフチェックリスト

  • userDefinitions[]内の各definitionIdが重複していないか
  • categoryIdがuserCategories内に実在するか
  • definitionTypeに応じてdefinitionData.elementIdが正しい値になっているか（sql→im_queryExecutor、javascript→im_scriptExecutor、rest→im_httpclient、template→im_templateProcessor）
  • inputDataDefinition・outputDataDefinitionが、entrypoint + typeDefinitionsの正しい構造になっているか（フロー定義編9章）
  • definitionオブジェクト全体が、単体で正しくJSONパースできるか（二重エンコードの崩れがないか）
  • このユーザ定義をフロー側から参照する場合、フロー側のkey.idがdefinitionIdと一致しているか（フロー定義編10.4節）
  • フロー側のマッピングルールが、このユーザ定義のoutputDataDefinitionで定義したプロパティ名と一致しているか

12. 未検証事項

  • userCategoriesが親子ツリー構造（flowCategories同様のparentId）をサポートするか。
  • 9章で挙げた8種類のdefinitionType文字列そのもの、およびdefinitionDataの内部構造。
  • JavaScript実行環境における制限対象APIの具体的な一覧（判定基準は7章で確認できているが、個別のAPI名は製品ドキュメントに明記されていない）。
  • outputDataDefinitionのbody型定義が、呼び出し先レスポンスの変化に応じてどう更新されるか（再度「JSON入力」が必要かなど）。
  • icon_data/（2章）の具体的な内部構造（画像ファイル形式、iconIdとの対応関係）。
  • 本章の手順で生成したZIP単体（フローを介さず、ユーザ定義ZIP自体）をインポートし、デザイナで開いて保存した場合に、フロー定義編で見られたような正規化（既定値の省略等）が同様に起きるか。
  • localize（単数形）に実際に多言語名を設定した場合の内部構造。
