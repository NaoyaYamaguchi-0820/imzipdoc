IM-LogicDesigner ZIP仕様 - ルーティング定義編

更新日: 2026-08-11

本書は、フロー定義ZIP（logicdesigner-zip-spec-flow.html）・ユーザ定義タスク登録ZIP（logicdesigner-zip-spec-userdef.html）と並ぶ第三のエクスポート形式、REST APIルーティング定義（flow_route.json）を対象とする。フローをREST APIとして外部公開する際のルーティング設定は、フロー本体のZIPには含まれず、この独立したZIP形式で管理される。

1. 概要

LogicDesignerで作成したフローをREST APIのエンドポイントとして公開する設定（ルーティングパス・HTTPメソッド・認証方式など）は、フロー画面からエクスポートするflow_definition.json形式のZIP（フロー定義編1〜18章）には一切含まれない。この設定は、flow_route.jsonという別形式のZIPとして個別にエクスポート・登録される。

2. ZIP構造

<route-export>.zip
└── flow_route.json

本書が対象とするサンプルはflow_route.json1ファイルのみで構成されている。公式の「IM-LogicDesigner仕様書」「4.5. インポート・エクスポート」によると、IM-LogicDesignerのエクスポート機能は本来、フロー定義・ユーザ定義・ルーティング定義を含む全データを一括で1つのZIPにまとめて出力するものであり、その場合のZIP構成は次のとおりとなる。

<export>.zip
├── flow_definition.json
├── flow_diagram/
│   └── <flowId>-<version>.png
├── user_definition.json
├── icon_data/
│   ├── designer/<iconId>
│   └── palette/<iconId>
└── flow_route.json

本書のサンプルのようにflow_route.json単体（あるいはフロー定義編・ユーザ定義編で扱った各サンプルのように他の1形式単体）で構成されたZIPも有効なエクスポート・インポート対象である。全体エクスポートと個別エクスポートのいずれの粒度でも、各JSONファイル自体の内部構造（本書が扱うflow_route.jsonの中身）は変わらないと考えられる。

3. トップレベル構造（配列）

flow_definition.json・user_definition.jsonとは異なり、トップレベルはオブジェクトではなく配列である。二重JSONエンコードも行われていない（配列要素は最初からJSONオブジェクトであり、文字列化されていない）。

[
  {
    "route": "sample_route",
    "method": "GET",
    "flowId": "sample",
    "version": -1,
    "authentication": "IMAuthentication",
    "authenticationParam": null,
    "authzUri": "im-logic-rest://sample_route",
    "secured": false,
    "responseType": "imJsonResponse",
    "responseHeader": {}
  }
]

配列の各要素が、1つのルーティング設定（1つのフロー×HTTPメソッドの組み合わせを外部公開する設定）に対応する。同一flowIdに対して、メソッド違いで複数のルーティングを定義することもできると見られる（未検証）。

4. エントリの項目

項目型・例説明
route文字列ルーティングパス。REST APIのURLの一部になる
method文字列HTTPメソッド。公式ドキュメントによるとGET・POST・PUT・DELETEが利用できる
flowId文字列このルーティングが呼び出す対象フローのflowId（フロー定義編6章参照）
version数値対象フローのバージョン。存在する具体的なバージョン番号、または最新バージョンを表す-1を指定できる
authentication文字列認証方式。公式ドキュメントによると3種類存在する。IMAuthentication（特別な認証処理を行わず、現在のCookieに紐づくセッションの認証状態のままロジックフローを実行する）、Basic認証（ユーザ名・パスワードで認証。マルチテナント環境では「ユーザコード」または「テナントID\ユーザコード」を指定可能）、OAuth（リクエストヘッダにAuthorization: Bearer <access_token>を付与して認証）
authenticationParam文字列またはnull認証方式に応じた追加パラメータ。IMAuthenticationではnull。Basic認証・OAuthの場合に指定する値の形式は未確認
authzUri文字列認可URI。im-logic-rest://<route>形式。IM-Authzによる認可判定に使われ、公式の「IM-LogicDesigner仕様書」「4.3. フロールーティング」によると、異なるフロールーティング間で同一の認可URIを指定することはできない（一意である必要がある）
secured真偽値セキュアトークンを使用するか。有効にすると、リクエストヘッダX-Intramart-Secure-Tokenまたはリクエストパラメータim_secure_tokenによるトークンチェックが行われる。トークンは同一セッション内で発行・使用する必要がある
responseType文字列レスポンスの変換方式。公式ドキュメントによると9種類存在する: JSON変換（内部識別子imJsonResponseを確認済み）、テキスト（出力データのbodyプロパティ値をそのまま返す）、HTML、XML、JSON文字列、任意Content-Type、ファイルダウンロード、ファイルインライン表示、ファイルバイナリ返却。imJsonResponse以外の内部識別子は未確認
responseHeaderオブジェクトレスポンスヘッダのキー・値。Content-Typeは、出力データ側のプロパティまたはこのresponseHeaderで指定でき、いずれも未指定の場合はapplication/octet-streamが適用される。サンプルでは空オブジェクト

5. REST API実行時の仕様

ZIP・JSONの構造そのものではなく、生成したflow_route.jsonが実際にどうREST APIとして動作するかについて、公式の「IM-LogicDesigner仕様書」「4.3. フロールーティング」で説明されている実行時仕様を補足する。

項目説明
URL形式<SCHEME>://<HOST>(:<PORT>)/<CONTEXT_PATH>/logic/api/${route}。${route}部分にrouteの値が入る
セッション管理リクエストヘッダX-Intramart-Sessionでkeep・once・neverのいずれかを指定できる。省略時はonceと同じ動作になる
エラーレスポンス通常application/json形式（{"error": true, "errorMessage": "..."}）で返却される。ステータスコードは、入力データ形式が不正な場合400、未認証の場合401、セキュアトークン検証失敗または認可権限がない場合403、対応するフロールーティングが存在しない場合404、フロー実行時のエラーの場合500
Swagger出力<CONTEXT_PATH>/all-api-docsで全REST APIの仕様、<CONTEXT_PATH>/api-docs/${category-id}で特定カテゴリの仕様をSwagger形式で取得できる
マルチテナント対応リクエスト情報からテナントを自動解決する運用の場合はURLにテナント情報を含める。自動解決を使わない場合、IMAuthenticationでは事前ログインが必要、Basic認証ではユーザ名を<テナントID>\<ユーザコード>形式で指定する

inputDataDefinition・outputDataDefinition（フロー定義編9章）の基本型は、REST APIの入出力ではJSONの型に変換される。公式の「IM-LogicDesigner仕様書」「4.3.14. JSON上でのデータの表現」による対応は次のとおり。

基本型（typeId）JSON表現備考
stringString
booleanBoolean
byte / character / short / integer / long / float / doubleNumber
bigdecimalString数値表現の文字列
bigintegerString整数表現の文字列
localeStringロケールIDを表す文字列
timezoneStringタイムゾーンIDを表す文字列
calendar / date / imdatetime / sqldate / sqltimestampStringISO 8601の拡張形式
map / objectObject
imduration / binary / any（非対応）JSON形式では表現できない
この型対応表はルーティング（REST API）仕様のページに掲載されているもので、フロー定義編9.2節に記載した基本型一覧（実際のフロー定義ZIPから確認できたstring・character・integer・double・boolean・date・sqldate・byte・storage・map・anyの11種類）よりも種類が多い。特にbyteはここではNumber（数値）として説明されており、フロー定義編で「バイト列（バイナリデータ）」として観測された用途との関係は未確認（バイナリデータを表す型は、本来は非対応のbinaryである可能性がある）。

6. 新規生成時の注意

  • flowIdは、対応するflow_definition.json側のフローのflowIdと一致させる。フロー本体とルーティング設定は別々のZIPで管理されるため、生成時にこの対応関係が崩れないよう注意する。
  • トップレベルは配列であり、flowCategories/flowDefinitionsのようなラッパーオブジェクトを持たない。
  • 二重JSONエンコードは不要（配列要素はそのままJSONオブジェクトとして記述する）。
  • routeの命名規則（使用可能文字、同一ルートの重複可否）は利用環境の制約を確認する。
  • 特定バージョンに固定する必要がない限り、versionは-1（最新バージョン）を指定しておくと、フロー側のバージョンを更新してもルーティング側の修正が不要になる。
  • secured: trueにする場合は、呼び出し側がX-Intramart-Secure-Tokenヘッダまたはim_secure_tokenパラメータでトークンを送信できるように、あわせて設計する。
  • authzUriは他のルーティングと重複しない値にする。

7. 未検証事項

  • 同一flowIdに対する複数ルーティング（メソッド違い等）の登録可否。
  • Basic認証・OAuthを指定した場合のauthenticationParamの具体的な形式。
  • imJsonResponse以外の8種類のresponseTypeの内部識別子文字列。
  • responseHeaderに値を設定した場合の具体的な構造（キー・値のペアか、それ以上の入れ子構造を持つか）。
  • 本ZIPに複数のルーティングエントリを含めた場合の挙動（一括登録されるか、1件ずつの扱いか）。
  • icon_data/（2章）の具体的な内部構造（ファイル形式、iconIdとユーザ定義側の対応関係）。
  • byte型がフロー定義ZIP内でバイナリデータ用途に使われている点と、ルーティング仕様上のJSON表現（Number）との関係。
