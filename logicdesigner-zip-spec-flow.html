IM-LogicDesigner ZIP仕様 - フロー定義編

更新日: 2026-08-11

本書では、IM-LogicDesignerのエクスポートZIPに含まれるデータの構成と、各データの役割を網羅的に説明する。ファイル構成や項目は、製品バージョン、エクスポート対象、フローの内容によって異なる場合がある。

本書はフロー定義ZIP（flow_definition.json）を対象とする。関連する別形式のZIPは別ファイルにまとめている。ユーザ定義タスク登録ZIP（user_definition.json）はlogicdesigner-zip-spec-userdef.html（ユーザ定義編）、REST APIルーティング定義ZIP（flow_route.json）はlogicdesigner-zip-spec-route.html（ルーティング定義編）を参照。

1. 概要

エクスポートZIPは、ロジックフローの定義情報（実行順序、入出力、マッピングなど）と、デザイナ上の表示情報（ノード配置、リンク、UI用メタデータ）をまとめて扱うためのアーカイブである。1つのZIPに、複数のカテゴリ・複数のフロー・同一フローの複数バージョンをまとめて格納できる。

なお、本書が対象とするのはフロー画面からエクスポートするflow_definition.json形式のZIPである。これとは別に、テナントに共有登録するユーザ定義タスク自体（key.type: "userDefinition"が参照する定義本体）を登録・移行するためのuser_definition.json形式のZIPや、フローをREST APIとして公開するルーティング設定を扱うflow_route.json形式のZIPが存在する。いずれもファイル構造・トップレベル項目が異なる別形式のエクスポートであり、別ファイル（ユーザ定義編・ルーティング定義編）で扱う。公式には、これらは1つのZIPに一括でまとめて出力することもできる（ルーティング定義編2章参照）。本書のサンプルはflow_definition.json単体で構成された個別エクスポートである。

2. ZIP構造

<export-file>.zip
└── flow_definition.json
└── flow_diagram/
    └── <flowId>-<version>.png
パス役割備考
flow_definition.jsonカテゴリおよびフロー定義本体単一ファイル。複数カテゴリ・複数フロー・複数バージョンをまとめて格納
flow_diagram/<flowId>-<version>.pngデザイナ画面のフロー図を画像化したものフロー定義の各バージョンに対応する画像を1枚ずつ格納。エクスポート対象によっては存在しない場合がある

フロー定義の件数とフロー図PNGファイルの件数は、必ずしも一致しない（図が生成されない、あるいはエクスポート対象外になるケースがある）。

3. flow_definition.json のトップレベル構造

{
  "flowCategories": [ { ... }, ... ],
  "flowDefinitions": [ "{...}", "{...}", ... ]
}
キー型説明
flowCategories配列フローを分類するカテゴリの一覧（JSONオブジェクトの配列）
flowDefinitions配列フロー定義の一覧。各要素はJSONオブジェクトではなく、JSONを文字列化した値（二重エンコード）
flowDefinitionsの各要素は文字列であるため、読み込む際は外側のJSONを解析した後、各要素をもう一度JSONとして解析（JSON.parseを2回）する必要がある。同様の二重エンコードは、フロー定義内のadditional.uiにも存在する（12章参照）。

4. flowCategories（フローカテゴリ）

項目型・例説明
categoryId文字列カテゴリを識別するID
categoryName文字列カテゴリ名（既定言語）
sortNumber数値表示順
localizesオブジェクト言語ごとのカテゴリ名。キーはロケール（ja、en、zh_CNなど）。7章参照
parentId文字列またはnull親カテゴリのcategoryId。nullはルート直下
displayName文字列画面に表示する名称（通常categoryNameと同値）

カテゴリは親子関係（parentId）でツリー構造を持てる。parentIdに他カテゴリのcategoryIdを指定すると、そのカテゴリの子として表示される。

{
  "categoryId": "category001",
  "categoryName": "サンプルカテゴリ",
  "sortNumber": 0,
  "localizes": {
    "ja": { "locale": "ja", "categoryName": "サンプルカテゴリ" },
    "en": { "locale": "en", "categoryName": "Sample Category" }
  },
  "parentId": null,
  "displayName": "サンプルカテゴリ"
}

5. flowDefinitions と二重JSON構造

flowDefinitions配列の各要素をJSON解析すると、1件のフロー（1つのflowId×version）を表すオブジェクトが得られる。同一flowIdでもversionが異なれば別要素として格納される（13章参照）。

categoryId文字列所属カテゴリのcategoryId

7. localizes（国際化情報）

カテゴリ名・フロー名の多言語対応に使用する。キーはロケール文字列、値はロケールと名称を持つオブジェクト。

"localizes": {
  "ja": { "locale": "ja", "flowName": "サンプルフロー" }
}

ロケールを持たないフロー・カテゴリではlocalizes: {}（空オブジェクト）となる。

8. constants（定数定義）

定数はフロー定義のconstants配列に格納する。マッピング定義から$const/<name>として参照する（11章参照）。

{
  "name": "CONST1",
  "value": "定数１",
  "typeId": "string",
  "description": "説明１",
  "common": false
}
項目説明
name定数ID。フロー内で定数を識別する名前。$const/<name>で参照
value定数値（文字列格納。typeIdに応じて実行時に解釈される）
typeIdデータ型。9.2節の基本型を指定できる
description定数の説明
common共通（テナント共有）定数かどうか

9. データ定義（入力・出力・変数）

inputDataDefinition、outputDataDefinition、variablesDataDefinitionはいずれも同一の構造（entrypoint + typeDefinitions）を持つ。

9.1 entrypoint と typeDefinitions

{
  "entrypoint": { "typeId": "root", "basic": false, "required": false, "listingType": "none" },
  "typeDefinitions": [
    {
      "id": "root",
      "properties": [
        { "typeId": "string",  "name": "input1",  "description": null, "listingType": "none", "required": false, "basic": true },
        { "typeId": "integer", "name": "integer1", "description": null, "listingType": "none", "required": false, "basic": true },
        { "typeId": "im_logic_object_1", "name": "object1", "description": null, "listingType": "none", "required": false, "basic": false },
        { "typeId": "string",  "name": "string1", "description": null, "listingType": "list", "required": false, "basic": true }
      ]
    },
    { "id": "im_logic_object_1", "properties": [ ... ] },
    { "id": "string",  "properties": [] },
    { "id": "integer", "properties": [] }
  ]
}
項目説明
entrypoint.typeIdルート型のtypeId。通常"root"で、typeDefinitions内の同名IDを参照する
typeDefinitionsこの定義内で使用する全ての型（ルート・複合型・基本型）の配列。基本型（string等）も参照用にproperties: []として列挙される
typeDefinitions[].id型ID。root、独自複合型ID（im_logic_object_1等）、基本型名のいずれか
typeDefinitions[].propertiesその型が持つプロパティ（項目）の配列
properties[].typeIdプロパティの型。基本型名またはtypeDefinitions内の複合型ID
properties[].nameプロパティ名
properties[].description説明（未設定時はnull）
properties[].listingTypenone（単一項目）またはlist（配列）
properties[].required必須項目かどうか
properties[].basic基本型かどうか（true=基本型、false=複合型）

複合型はネスト可能で、ある複合型のプロパティがさらに別の複合型を参照できる（例: im_logic_object_1のプロパティがim_logic_object_2を参照）。ネストの段数に明示的な上限はない。

9.2 基本型（typeId）一覧

typeId説明
string文字列
character文字（1文字）
integer整数
double浮動小数点数
boolean真偽値
date日付
sqldateSQL日付型（データベース連携タスクの入出力で使用）
byteバイト列（バイナリデータ）

上記以外のtypeIdは独自定義の複合型（typeDefinitions内のid）を指す。命名は自動採番（im_logic_object_N）またはユーザ指定名になる。

上表は実際のフロー定義ZIPから確認できた基本型である。公式の「IM-LogicDesigner仕様書」「4.3.14. JSON上でのデータの表現」（ルーティング定義編5章に型対応表を転記）によると、基本型にはこのほかにもshort・long・float・bigdecimal・biginteger・locale（ユーザ定義編9章参照）・timezone・calendar・imdatetime・imduration・sqltimestamp・binary・objectが存在する。これらは実際のフロー定義ZIPのサンプルでは未観測のため、上表には含めていない。

9.3 配列・単一項目

  • 配列: listingTypeに"list"を指定する
  • 単一項目: listingTypeに"none"を指定する

10. flowElements（フロー要素）

フローは、flowElements配列に格納されたノードと接続の集合として表現される。全要素が同一の外形（下表）を持ち、種別ごとにpropertiesの中身が異なる。

10.1 共通項目

項目型説明
executeId文字列フロー内で一意な要素ID。マッピングの参照キー（<executeId>/<path>）としても使用
alias文字列またはnull要素の別名。未設定時はnull
keyオブジェクト要素種別の識別情報。type・id・versionを持つ。10.2節参照
label文字列またはnullデザイナ上の表示ラベル。接続要素ではnullになることが多い
comment文字列またはnull要素に対するコメント
propertiesオブジェクト要素固有の設定。要素種別ごとに項目が異なる（15章の早見表を参照）
mappingDefinitionオブジェクトまたはnullマッピングルールの集合。接続専用要素（im_sequence等）ではnullになる。11章参照

10.2 key.type の種類

key.type説明
application標準アプリケーション（IM-LogicDesigner組み込みの制御要素・標準タスク）。key.idで種別を識別
userDefinitionテナント内で共有登録されたユーザ定義タスク（SQL実行定義、他フロー呼び出し用フロー、外部連携など）への参照。定義本体はZIP外（登録済みのユーザ定義）にあり、要素側はkey.id（定義ID）で参照するのみ
localUserDefinitionそのフロー内だけで有効なユーザ定義タスク。定義本体を要素のproperties.definitionにそのまま埋め込む（10.5節参照）

key.versionは、userDefinitionの特定バージョンを固定したい場合に使用する項目で、固定しない場合はnullとなる。

10.4 userDefinition要素（共有ユーザ定義タスク）

key.type: "userDefinition"の要素は、定義本体を持たず、テナントに登録済みの定義をkey.idで参照するのみである。要素自身のpropertiesは通常continueOnError程度に限られ、入出力の受け渡しはmappingDefinition.mappingRulesで行う。この定義本体自体の登録・エクスポート形式（user_definition.json）はユーザ定義編を参照。

{
  "executeId": "userTask1",
  "alias": null,
  "key": { "type": "userDefinition", "id": "SampleUserDefinedTask", "version": null },
  "label": "サンプルユーザ定義タスク",
  "comment": "",
  "properties": { "continueOnError": false },
  "mappingDefinition": {
    "mappingRules": [
      { "id": "de0391bf-...", "target": "userTask1/param1",
        "source": { "type": "value", "name": null, "path": "$input/param1", "arguments": null } }
    ]
  }
}

10.5 localUserDefinition要素（フロー内埋め込みユーザ定義タスク）

key.type: "localUserDefinition"の要素は、そのフロー専用のユーザ定義タスクであり、定義本体全体をproperties.definitionにインライン埋め込みする。他フローからは参照されない。

項目説明
properties.definition.definitionId定義ID（通常executeIdと同値）
properties.definition.version定義のバージョン
properties.definition.categoryId定義のカテゴリ（未分類は空文字）
properties.definition.definitionType定義の種類（例: "sql"＝SQL実行タスク）。内部で実行する処理の種類に応じた値を取る
properties.definition.definitionName定義名（デザイナ上の表示名）
properties.definition.sortNumber表示順
properties.definition.definitionData.elementId実処理を行う内部要素ID。SQLタスクではim_queryExecutor
properties.definition.definitionData.elementProperties内部要素固有の設定。SQLタスクではquery（SQL文）、queryType（SELECT等）、databaseType（TENANT等）、connectId、limitationを持つ
properties.definition.definitionData.inputDataDefinition / outputDataDefinitionこの定義固有の入出力データ定義（構造は9章と同様）

マッピングルールが競合する場合の優先順位
  • ターゲットパスの詳細さ（特異性）が異なる場合: 範囲が重なる複数のルール（例: target: "$output"という一括ルールと、target: "$output/message"という個別ルール）が存在すると、ターゲットパスがより詳細（狭い）なルールが優先される。この優先順位はmappingRules配列内の並び順とは無関係で、個別ルールを一括ルールより後ろに置いても、前に置いても結果は変わらない。
  • ターゲットパスが完全に同一の場合: 同じtarget（例: "$output/message"）を持つルールが複数存在すると、mappingRules配列内で後方にあるルールが優先される（逐次上書きに近い挙動）。

mappingOrder（6章）がこれらの優先順位の決定に関与している可能性がある。mappingOrder: "SOURCE_HIERARCHY"の場合の挙動であり、"TARGET_HIERARCHY"など他の値で優先順位が変わるかは未確認。

12.5 mapping.json（グラフィカルマッピングの内部構造）

要素がmappingDefinition.mappingRulesを持つ場合、対応するdataMap[uiNodeId].mapping.jsonも正しい内容で埋める必要がある。空{}のまま（またはmappingRulesと不整合な内容）にしてZIPを生成すると、ZIP自体のインポートは成功しても、デザイナでそのフローを開いて保存した時点でmappingRulesが消去される（マッピング先の出力が全てnullになる）。mapping.jsonは単なる表示用の付随データではなく、デザイナが実際のマッピング内容の正とみなすデータである可能性が高い。

mapping.jsonは、その要素のmappingRulesをグラフィカルエディタ上で表現するための、独立した小さなノード・接続グラフである。

sizeキャンバスのサイズ（width/height）。観測範囲ではいずれも{"width":400,"height":500}で固定値の可能性がある

12.5.1 connectors の構造

単純な値参照（関数を使わないmappingRules）の場合、1件のmappingRules要素が1件のconnectors要素に対応する。

{
  "id": "f5c0f789-d437-475e-8d80-9b83eb44038d",
  "source": {
    "id": "7a9878c6-a8a6-4700-9ba8-2c7920af62f0",
    "type": "$input",
    "path": "sample_mock_response_generate1\tstatus",
    "port": "out"
  },
  "target": {
    "id": "e94a3b4d-9014-4c45-aa5f-7031a141bad6",
    "type": "$output",
    "path": "$output\tstatus",
    "port": "in"
  }
}
項目説明
id対応するmappingRules[].idと同一のUUIDを指定する。この一致によって、JSON側のルールとグラフィカル表示側の接続が結び付けられていると考えられる
source.id / target.idこのマッピングキャンバス内でのみ有効な、新規発行のUUID（mappingRules側の値とは無関係）
source.type参照元ノードの種別。単純な値参照の場合は、実際の参照先（$variable／$const／他要素の出力等）によらず常に"$input"になると見られる。参照元が関数呼び出しの場合は関数名（例: "im_string_join"）
target.type設定先ノードの種別。単純な値設定の場合は、mappingRules[].targetの実際のプレフィックス・種類（$output／$variable／他要素の入力プロパティ等）によらず常に"$output"になる（source.typeが実際の参照先によらず常に"$input"になるのと対の規則）。設定先が関数の引数の場合は関数名
source.path / target.path参照元・設定先のパス。mappingRules側とは異なり、区切り文字がスラッシュ（/）ではなくタブ文字（\t）である（例: "$variable\twk_result"、"sample_mock_response_generate1\tstatus"）。mappingRules側のパスが2階層以上ネストしている場合（例: "userTask1/status/statusCode"）も、スラッシュを単純にタブへ置き換えるだけでよい（"userTask1\tstatus\tstatusCode"）
source.port / target.port接続点。参照元は通常"out"、設定先は通常"in"。関数への引数が複数ある場合、設定先は"in1"、"in2"のように連番になる

関数呼び出しを伴うmappingRules（source.type: "function"、11.5節）の場合は、関数ノード自体もconnectorsの中間ノードとして表現され、複数のconnectors（各引数→関数、関数→設定先）に展開される。関数ノードのidはattrsのキーとしても使われ、キャンバス上の座標を持つ。この場合、mappingRules[].idと一致するのは、関数の出力を最終的な設定先へつなぐconnectors要素のみである。

mappingRulesを持たない要素（mappingRules: []）については、対応するmapping.jsonを{ "version": 1, "attrs": {}, "connectors": [], "size": {...} }のような空の状態のままにしても問題ないと見られる。

11.2節の一括（構造的）マッピングを使う場合も、connectorsの構造は変わらない。source.path・target.pathにサブパスなしのプレフィックスのみ（例: "userTask1"、"$output"）を指定した1件のconnectors要素になるだけで、個々の子プロパティごとにconnectorsを分ける必要はない。

13. 複数フロー・バージョンの格納

1つのflow_definition.jsonには、複数のカテゴリと複数のフロー定義を格納できる。flowCategoriesはカテゴリの配列、flowDefinitionsはフロー定義（二重JSON文字列）の配列である。

同一のflowIdに対して複数のバージョンを格納できる。各バージョンはversion（1起点の整数）で識別し、フロー名やカテゴリが同じでも、定義内容・フロー要素・図をバージョンごとに個別のエントリとして保持する。バージョンは通常1から連番で付与される。

14. フロー図（flow_diagram）との対応

フロー図はflow_diagram/<flowId>-<version>.pngとして格納する。複数バージョンを持つフローでは、バージョンごとに異なる画像ファイルを持つ（例: <flowId>-1.png、<flowId>-2.png、...）。

ZIP内のフロー定義とフロー図を対応付ける際は、flowIdとversionをキーとしてファイル名（<flowId>-<version>.png）を組み立てる。ファイル名に使用できない文字や、同名となるIDの扱いは利用環境の制約を確認する。フロー定義側のエントリ数とフロー図ファイル数は必ずしも一致しない（図が生成されない、あるいはエクスポート対象外になるケースがある）ため、突合時は欠落を許容する。

16. 生成・変更時の注意

  • フロー図のファイル名は<flowId>-<version>.pngの形式で定義との対応を表す。
  • flowDefinitionsとadditional.uiは二重JSON解析が必要である。
  • UIのノードID、dataMap、graph.cells内のリンク参照（source.id/target.id）は、フロー定義側のexecuteId・startPoint/endPointと整合させる。
  • カテゴリID、フローID、バージョン、図ファイル名の対応を崩さない。
  • mappingOrder・versionCommentのようにエクスポート元によって有無が変わる項目があるため、キー欠落を前提に読み込み処理を実装する。
  • 定数（constants）を追加・変更する場合は、定義自体だけでなく、各要素のmappingDefinition.mappingRules内の$const/<name>参照との整合性も確認する。
  • 仕様の詳細は、利用するintra-mart環境のバージョンとエクスポート対象に応じて確認する。

17. 対象範囲・未網羅事項

本書は、ZIPの構造、フロー定義、デザイナ表示情報の一般的な仕様を対象とする。以下は本書の対象外であり、詳細を確認できていない。

  • key.version（userDefinitionのバージョン固定）が非nullとなるケースの挙動。非nullの実例は確認できていない
  • ユーザ定義タスクの処理種別のうち、definitionDataの内部構造まで確認できているのは"sql"・"javascript"・"rest"・"template"の4種類のみ（ユーザ定義編6〜9章）。公式ドキュメントによると全17種類の処理種別が存在し、残る13種類はelementIdやdefinitionType文字列は未確認（一部はelementPropertiesの項目名まで判明。ユーザ定義編10章）
  • フロートリガのeventId（発生条件）に指定できる値の全量（確認できているのはim_account_createdのみ）

「ユーザ定義タスク自体の登録フォーマット」はユーザ定義編で解決した。

なお、フロー起動条件・トリガ（スケジュール実行やイベント起動等の設定）に関する記述はflow_definition.json内には見当たらない。フロー本体の定義のみが含まれ、起動条件はLogicDesigner外の別画面・別データで管理されている。公式の「IM-LogicDesigner仕様書」「4.4. フロートリガ」によると、LogicDesigner自身にも「フロートリガ」という起動条件設定の仕組みがあり、発生条件が満たされた際にIM-Propagationを介してデータを受信しフローを実行する。フロートリガはflow_trigger.jsonという独自のZIP形式でエクスポートされることを確認済みで、flow_route.json（ルーティング定義編）と同様にトップレベルが配列で、二重JSONエンコードは行われない。

18. 新規ZIP生成手順（実践ガイド）

専用の生成ツールを介さず、本書の内容だけを頼りにゼロからflow_definition.jsonとZIPを組み立てる場合の実践的な手順をまとめる。

18.1 全体の手順

  1. flowCategoriesを用意する（最低1件）。4章参照。
  2. フロー定義オブジェクト（二重エンコード前の生JSONオブジェクト）を6章の項目一覧に従って組み立てる。versionComment・mappingOrderは省略可能で、迷う場合はキー自体を含めない方が安全（これらのキーを持たないエクスポートも存在する、6章）。
  3. flowElementsを組み立てる。まずim_startからim_endまでをim_sequenceで一筆書きに繋ぎ、そのあとで分岐・ループ・タスクを追加していく。executeIdはフロー内で一意にする（im_sequenceのexecuteIdは<startPoint>_<endPoint>形式が使われることが多いが、一意でありさえすれば必須の命名規則ではない）。
  4. 各要素のmappingDefinition.mappingRulesを設定する（11章）。制御要素・接続要素の扱いは18.2節のスケルトンを参照。
  5. additional.ui（graph.cells・dataMap・optionMap）をflowElementsから機械的に生成する。18.3〜18.4節参照。
  6. フロー定義オブジェクトをJSON.stringifyし、flowDefinitions配列の要素（文字列）として格納する（二重エンコード、5章）。
  7. トップレベル{ flowCategories, flowDefinitions }をJSON化し、UTF-8でflow_definition.jsonとして保存する。
  8. 18.5節のセルフチェックリストで整合性を確認する。
  9. ZIPへパッケージングする（18.6節）。

18.4 要素追加時の「3点セット」

フローに要素を1つ追加するたびに、次の3か所を必ず同時に更新する。いずれかを欠くと、flowElementsとUI情報（additional.ui）の対応が崩れる。

  1. flowElements配列に新しい要素を追加する
  2. 実行順を表すim_sequence要素を追加・更新し、前後の要素のexecuteIdをstartPoint/endPointで正しく参照する
  3. additional.uiのgraph.cells（新規ノード＋関連するlink）・dataMap・optionMapに対応エントリを追加する（im_sequence要素自体はgraph.cellsのlinkとしてのみ表現し、dataMap・optionMapには追加しない。12.2節参照）。追加した要素がmappingRulesを持つ場合は、dataMap[uiNodeId].mapping.jsonにも同じ内容を反映する（12.5節）

18.5 生成後セルフチェックリスト

ZIP化する前に、生成したflow_definition.json（二重エンコード前の状態）に対して確認する。

  • 各flowElements[].executeIdがフロー内で重複していないか
  • im_sequence／im_startLoop／im_endLoop／im_gatewayのproperties内で参照するexecuteId（startPoint/endPoint/defaultRoot等）が、実在する要素のexecuteIdと一致しているか
  • additional.uiのgraph.cells内linkのsource.id/target.idが、対応するノードのid（dataMapのキー）と一致しているか
  • dataMap・optionMapのキー（UIノードID）が、graph.cells内の対応するノードのidと一致しているか
  • im_sequenceを除くflowElementsの件数と、dataMap・optionMapのエントリ数が一致しているか
  • mappingDefinition.mappingRules[].target・source内のpathが指す先（他要素のexecuteId、$variable/$const/$input/$outputの名前）が実在するか
  • constantsを追加・変更した場合、対応する$const/<name>参照側と整合しているか（16章）
  • mappingRulesを持つ要素について、対応するdataMap[uiNodeId].mapping.jsonのconnectorsが、mappingRulesと同じ件数・同じidで存在するか（12.5節。ここが不整合だとデザイナでの再保存時にルールが消える）
  • フロー定義オブジェクト・additional.uiそれぞれが、単体で正しくJSONパースできるか（二重エンコードの崩れがないか）
  • flowId・version・categoryIdが、flowCategoriesおよび同一ZIP内の既存フローと矛盾しないか

18.6 ZIPパッケージング時の注意

  • flow_definition.jsonはUTF-8で保存し、ZIPのルート直下に配置する（2章）。
  • フロー図（flow_diagram/<flowId>-<version>.png）を含めるかどうかは18.7節を参照。含めない場合はディレクトリごと省略してよい（2章のとおり、件数の不一致は許容される）。
  • 二重エンコードした文字列（flowDefinitionsの各要素、additional.ui）の中に、エスケープされていない実改行や制御文字を含めない。
18.7 生成・保存にまつわる補足事項
  • flow_diagramディレクトリを含めない状態、標準的な圧縮方式（特別なファイル順序の調整なし）でも、ZIPのインポートは行える。
  • dataMap[uiNodeId].mapping.jsonを{}のまま省略すると危険。ZIPのインポート自体は成功するが、そのフローをデザイナで開いて保存した時点で、対応するflowElements[].mappingDefinition.mappingRulesが消去される（マッピング先の出力が全てnullになる）。正しい構造は12.5節を参照。
  • フロー図（PNG）は、エクスポート時にツール側が自動生成する。インポート時にPNGの有無は問われないと見られる。
  • additional.ui内で独自に発行したUUID（ノードID等）は、インポート後もそのまま維持される（デザイナ側で再発行されることはない）。
  • ノードのposition（座標）は、簡易な配置でも動作上の問題は生じない。
  • デザイナで一度保存すると、properties内で既定値（例: continueOnError: false）のキーが省略される、mappingOrderが明示的に付与される（値の例: SOURCE_HIERARCHY）など、正規化が行われる場合がある。生成時にこれらのキーを明示していても、インポート・動作には影響しないと見られる。
